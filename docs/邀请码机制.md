# 邀请码准入机制

> 本文档记录当前生效的准入机制。它是对原始设计文档(`docs/PRD-P0` F1、`docs/技术架构设计` §5.3/§6.1、`docs/开发计划` B3/H2 描述的「微信手机号验证 + 白名单」)**的偏离与替代**——原始设计因手机号敏感、微信组件开通成本等已弃用,改用「一人一码邀请码」。原始文档章节保留作历史参考,以本文为准。

## 设计决策(用户拍板)

1. **一人一码**:每个邀请码限用一次,用即失效(`unused`→`used`)。
2. **彻底移除手机号**:注册不再要手机号,`User` 删 `phone`/`phone_masked`、删 `idx_user_phone`。
3. **作用域 = 小程序准入资格**(全局,不绑活动):码只决定「这个微信号有没有资格用本小程序」,验证通过后该 `openid` 即合法用户,参加任何活动都不再需要码。步数/排名本就走 openid,去手机号无副作用。

## 数据模型

**InviteCode 集合**(`cloudfunctions/schema/collections.js`):
```
{ _id, code(unique), status(unused|used|disabled), used_by(openid, onlyServer), used_at,
  batch_id, created_by(onlyServer), created_at, note }
```
索引:`idx_invite_code`(code 唯一,原子消费依赖它)、`idx_invite_status`(status 普通索引)。

**User 变更**:删 `phone`/`phone_masked`,新增 `invite_code`(注册时写入用的码,审计/admin 列表用,无唯一索引——码一次性不会冲突)。

## 流程

### 注册准入(`auth.register`)
1. `login` 只查 `User` by openid,判新老(`is_new` 引导注册向导);老用户(`User` 存在)`registered:true` 免码。
2. 注册向导提交(昵称+头像+邀请码)→ `auth.register`。
3. `registerUser`(`auth/authRegister.js`):先查 User(已存在→幂等返回,不重复消费码)→ 校验昵称/码 → `consumeCode`(原子消费)→ `add` User(写 `invite_code`)。

### 原子消费(`auth/inviteCode.consumeCode`)
`where({code, status:'unused'}).update({status:'used', used_by, used_at})` → `stats.updated===1` 成功;`updated===0` 二次 `where({code}).get()` 消歧:已用→`BIZ_INVITE_CODE_USED`、禁用→`BIZ_INVITE_CODE_DISABLED`、不存在→`BIZ_INVITE_CODE_INVALID`。依赖 `idx_invite_code` 唯一索引确保并发仅一个命中。

### 邀请码管理(`admin.inviteCode.*`)
- `generate`:管理员批量生成(`generateCodes` 纯函数,`rand` 注入,内存去重)→ `generateInviteCodesToCloud` 批量 add(逐条 try/catch + written/failed)。
- `list`:列表+分页+状态筛选(`listCodes`),投影**不下发 `used_by` 原始 openid**。
- `disable`:禁用未用码(`disableCode`,仅 `unused` 可禁用;已用码已绑定用户不可改)。

## 错误码(`common/errors.js`)
- `BIZ_INVITE_CODE_INVALID: 2011`(不存在/格式错)
- `BIZ_INVITE_CODE_USED: 2012`(已用)
- `BIZ_INVITE_CODE_DISABLED: 2013`(已禁用)
- 缺码复用 `BIZ_PARAM_MISSING: 2005`
- 已删:`BIZ_NOT_IN_WHITELIST:2001`、`BIZ_PHONE_TAKEN:2007`

## 邀请码格式
6 位 Crockford Base32(字母表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`,排除 I/L/O/U),大写无横线存储。输入侧宽容解码(`O→0` / `I或L→1` / `U→V`、转大写、去空格横线)——因生成的码不含这些字符,出现即误读。码空间 32^6≈10^9 +「必须 `unused` 才有效」,暴力枚举几乎不可能命中未用码。

## 跨域拆分(关键)
`sync-shared` 的 `SHARED_DIRS=['common','steps','activity','dept','schema']`,**auth/admin/user 不可共享**——`auth.register` 不能 require `admin/`。故邀请码逻辑拆两处:`auth/inviteCode.js`(注册消费 `consumeCode`)、`admin/inviteCode.js`(生成/列表/禁用);Crockford 格式助手跨两域各保留一份(符合现有 `normalizePhoneInput` 双份惯例,避免改 `SHARED_MANIFEST`)。**无新跨目录 require,manifest 不变。**

## 超管冷启动
去手机号后无 `SUPER_ADMIN_PHONE`。第一个超管**直接在云开发控制台把 `User.is_admin` 改 `true`**(唯一方式)。之后超管可在 app 内「用户管理」用 `admin.setAdmin` 任命他人(禁止自我降级 `BIZ_SELF_DEMOTE_FORBIDDEN:2006`)。

## 部署清单
1. 部署云函数(`auth`/`user`/`admin` 必改;因 `_shared`(errors/mask)变更,建议全 8 包重传);
2. 调 `admin.ensureSchema` 或云控制台手建 **InviteCode 集合 + `idx_invite_code` 唯一索引**——**生码前必须存在唯一索引**(否则并发生成可能产重复码);
3. 管理员在「邀请码管理」页生成一批码,分发给员工;
4. 前端发版(注册向导 / profile 去手机号 / 新 inviteCode 管理页 / dashboard 已发码数指标);
5. 通知老用户免码登录(`User` 存在即已准入);`SUPER_ADMIN_PHONE` 环境变量若已配将失效(代码已删该路径)。

## 已知边界
- 消费码后建号失败(极罕见)会浪费码,管理员重生成即可,**不做回滚**(回滚引入新竞态,得不偿失)。
- 遗留 `phone=''` 占位 User 在新规则下 `registered:true`(本就是真实 openid 用户,无害)。
- Whitelist 集合数据与旧索引(`idx_user_phone`/`idx_whitelist_phone`)保留无害(代码已不引用,生产可选手动清理)。
