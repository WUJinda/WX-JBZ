## 1. 产品概述

### 1.1 项目背景
企业希望组织一场面向全体员工的健步走活动，通过运动打卡促进员工健康、增强团队凝聚力。活动形式为**单期限时**（有明确起止日期，结束后归档），激励机制以**虚拟荣誉勋章**为主，兼顾低成本与参与感。

### 1.2 产品目标
| 维度 | 目标 |
|------|------|
| 业务目标 | 完成一场覆盖全员的健步走活动运营，提升员工健康意识与团队凝聚力 |
| 用户目标 | 员工便捷记录步数、查看个人/部门排名，获得参与感与荣誉感 |
| 产品目标（P0） | 跑通"登录—报名—步数同步—排名展示"核心闭环，支撑单期活动完整落地 |

### 1.3 目标用户
- **普通员工（参与者）**：企业全体员工，通过微信授权+手机号登录参与。
- **活动管理员（HR/行政）**：负责活动配置、数据查看、进度把控。

### 1.4 核心价值
- 员工零门槛参与（微信内直接使用，无需额外 App）。
- 步数自动获取（接入微信运动，无需手动记录）。
- 部门天然成队，激发跨部门良性竞争。

## 2. 范围定义

### 2.1 P0 包含功能

| 编号 | 模块 | 说明 |

| F2 | 部门选择 | 报名时选择部门，**部门即团队**，自动归属 |
| F3 | 微信运动步数同步 | `wx.getWeRunData` 授权 + 后端解密，每日同步当日及历史步数 |
| F4 | 步数展示 | 当日步数、累计步数、趋势图、历史记录 |
| F5 | 个人排行榜 | 个人累计步数总榜 + 我的排名 |
| F6 | 部门排行榜 | 部门（团队）累计步数榜 + 部门内明细 |
| F7 | 活动主页 | 活动信息、规则、起止时间、当前阶段、报名入口 |
| F8 | 简单后台 | 活动配置、用户/部门查看、数据看板 |

### 2.2 P0 明确排除（后续规划）

| 阶段 | 功能 | 说明 |
|------|------|------|
| P1 | 每日打卡任务、每日目标步数 | 任务体系与留存机制 |
| P1 | 勋章体系、勋章墙、称号等级 | 虚拟荣誉激励 |
| P2 | 电子证书、战绩海报、朋友圈分享 | 成就外化与传播 |
| P2 | 同事点赞/加油互动 | 社交互动 |
| P2 | 连续打卡挑战、阶段性里程碑任务 | 长期参与玩法 |

> P0 在数据结构上预留字段（如 `badge`、`check_in`），但前端不实现相关逻辑。
>
> **积分体系（实际已实现，补充说明）**：P0 虽未在原始 PRD 中规划积分，但代码已实现轻量积分体系（规则于 2026-08-17 调整为现行版本，对标 F1 名次分制）：
>
> - **个人名次分**：活动结束后按最终个人累计榜结算，前 10 名分别 +12/+10/+8/+7/+6/+5/+4/+3/+2/+1；`total_steps<=0` 的名次跳过且不递补（有效步数人数不足 10 时靠后名次分作废）。
> - **部门奖**：部门榜第 1 名（非小样本部门）的所有参赛人员（含 0 步成员）每人 +2；若所有部门均为小样本则跳过部门奖。
> - **叠加**：个人奖与部门奖可叠加（同人两笔相加）。
> - **手动调整**：管理员可在后台手动增减积分（delta 整数可负），结果不允许为负（扣减后不足 0 兜底为 0）。
> - **台账展示**：后台积分台账按积分降序 → 同分按累计步数降序 → 再同按 _id 升序排序。
>
> 当前仅存余额字段 `User.points`，**无积分流水台账**（无法追溯单笔变更历史），如需审计能力须后续补充流水表。

## 4. 核心业务流程

### 4.1 首次参与流程
```
打开小程序
  └─> 活动主页（游客可见活动介绍/规则）
        └─> 点击「报名参加」
              └─> 微信授权登录（获取 openid/unionid + 用户头像/昵称）
                    └─> 手机号验证（微信手机号快速验证 或 短信验证码）
                          └─> 校验手机号是否在企业员工白名单
                                ├─ 通过 ─> 选择部门 ─> 完成报名 ─> 进入个人主页
                                └─ 不通过 ─> 提示"非企业员工，无法参与"
```

### 4.2 日常使用流程
```
打开小程序（已登录已报名）
  └─> 个人主页（自动触发步数同步）
        ├─ 查看当日步数 / 累计步数 / 趋势图
        ├─ 查看个人排行榜（我的排名 + 前后相邻名次）
        └─ 查看部门排行榜（我的部门排名 + 部门内明细）
```

### 4.3 步数同步流程
```
用户进入小程序 / 下拉刷新
  └─> 检查今日是否已同步
        ├─ 未同步 ─> 调用 wx.getWeRunData（首次需用户授权）
        │     └─> 携带 encryptedData + iv 提交后端
        │           └─> 后端用 session_key 解密，取最近 N 天 stepInfoList
        │                 └─> 落库/更新（按日去重，取当日值）
        │                       └─> 返回最新累计步数，前端刷新
        └─> 已同步且距上次<阈值 ─> 直接读缓存（减少频繁授权打扰）
```

### 4.4 活动结束流程（P0）
```
到达活动截止时间
  └─> 步数同步入口关闭（排名冻结）
        └─> 排行榜展示最终名次（按截止时累计步数）
              └─> 活动主页状态置为"已结束"
                    └─> 用户仍可查看历史战绩（P0 仅展示，不发奖/不发证书）
```

## 5. 功能需求详述

### F1 登录与用户

**用户故事**
> 作为员工，我希望通过微信一键登录并验证手机号，以便快速参加活动且企业能确认我的身份。

**前置条件**
- 用户在微信环境内打开小程序。
- 用户手机号在企业员工白名单内（白名单由管理员后台导入）。

**页面与交互**
| 页面 | 元素 | 操作 |
|------|------|------|
| 活动主页（未登录） | 活动介绍、规则、「报名参加」按钮 | 点击「报名参加」唤起登录流程 |
| 登录授权页 | 微信授权登录按钮 | 点击触发 `wx.login` + `wx.getUserProfile` |
| 手机号验证页 | 「微信手机号快速验证」按钮（`open-type="getPhoneNumber"`） | 点击授权手机号；备选短信验证码 |
| 部门选择页 | 部门列表（管理员预设） | 单选部门后确认 |
| 个人资料页 | 头像、昵称、手机号（脱敏）、部门、累计步数 | 编辑昵称/头像（可选） |

**字段定义**
| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| openid | string | 是 | 微信唯一标识，主关联键 |
| unionid | string | 否 | 跨小程序识别（预留） |
| 昵称 nickname | string | 是 | 取微信昵称或自填 |
| 头像 avatar | string(URL) | 是 | 取微信头像或自传 |
| 手机号 phone | string | 是 | 经脱敏存储（138****1234） |
| 部门 dept_id | string | 是（报名后） | 关联部门表 |
| 报名状态 join_status | enum | 是 | 未报名/已报名 |

**业务规则**
- R1.1 一个手机号（一个 openid）仅能对应一个员工账号，禁止重复报名。
- R1.2 手机号必须在管理员导入的白名单内，否则拒绝报名并提示"非企业员工"。
- R1.3 登录态有效期 7 天，过期需重新静默登录（`wx.login`，无需用户再操作）；手机号验证态在活动期内有效，无需重复验证。
- R1.4 头像/昵称允许修改，部门报名后**不可自行修改**（如需调整联系管理员）。
- R1.5 手机号展示与存储均脱敏；后端以完整手机号做白名单匹配。

**涉及接口**
| 接口 | 入参 | 出参 |
|------|------|------|
| `POST /auth/login` | code（wx.login 返回） | token、是否已注册 |
| `POST /auth/phone` | encryptedData、iv（或手机号+短信码） | 手机号校验结果、是否在白名单 |
| `GET /user/profile` | token | 用户资料 |

### F2 部门选择

**用户故事**
> 作为员工，我希望报名时选择自己所属部门，以便我的步数能计入部门团队成绩。

**前置条件**
- 管理员已在后台预设部门列表。
- 用户已通过登录与手机号验证。

**页面与交互**
| 页面 | 元素 | 操作 |
|------|------|------|
| 部门选择页 | 部门列表（名称） | 单选 → 点击「确认加入」 |

**字段定义**
| 字段 | 类型 | 说明 |
|------|------|------|
| dept_id | string | 部门唯一标识 |
| dept_name | string | 部门名称 |
| 成员数 member_count | int | 部门已报名人数（展示用） |

**业务规则**
- R2.1 部门即团队，选择部门即自动归属该部门队伍，无独立"创建/加入团队"操作。
- R2.2 一个员工仅归属一个部门；报名后部门不可自行更改。
- R2.3 部门列表由管理员维护，员工不可新增部门。
- R2.4 若员工不确定部门，可联系管理员后台调整（P0 不提供员工自助改部门）。

**涉及接口**
| 接口 | 入参 | 出参 |
|------|------|------|
| `GET /dept/list` | — | 部门列表 |
| `POST /user/join` | dept_id | 报名结果、用户资料更新 |

### F3 微信运动步数同步

**用户故事**
> 作为员工，我希望小程序自动读取我的微信运动步数，以便无需手动记录即可参赛。

**前置条件**
- 用户已登录且完成报名。
- 首次同步需用户授权「微信运动」数据访问。

**页面与交互**
| 场景 | 交互 |
|------|------|
| 首次报名成功后 | 引导授权微信运动（点击按钮触发 `wx.getWeRunData`） |
| 进入个人主页 | 后台静默同步（若距上次同步>阈值） |
| 拒绝授权 | 提示"需授权微信运动才能参与排名"，提供「重新授权」入口（引导 openSetting） |
| 同步中 | 顶部加载提示；同步成功 Toast「步数已更新」 |

**字段定义**
| 字段 | 类型 | 说明 |
|------|------|------|
| user_id | string | 关联用户 |
| date | date | 步数日期（YYYY-MM-DD） |
| steps | int | 当日步数 |
| activity_id | string | 关联活动 |
| synced_at | datetime | 同步时间 |

**业务规则**
- R3.1 步数通过 `wx.getWeRunData` 获取 `encryptedData`，由后端用 `session_key` 解密得到 `stepInfoList`（最近 30 天每日步数）。
- R3.2 后端按日去重落库：同一 user_id + activity_id + date 取**最新同步值**覆盖。该唯一约束由 sync 逻辑用事务（或先查后写）保证（云数据库无原生唯一约束），防止同用户短时多次同步产生重复记录。
- R3.3 同步频率控制：同一用户同一天最多落库 N 次（建议 6 次/日），避免恶意刷接口；前端缓存最近一次同步时间，间隔小于阈值（建议 30 分钟）则直接读缓存。
- R3.4 **步数时效口径**（重要）：微信运动当日步数通常次日上午才趋于准确；排行榜累计步数统一按"**已同步且已入库**"的数据计算，**每日次日 12:00（可配置）锁定前一日最终值**。锁定时间选在次日中午而非 00:00，是为了给用户整个上午补同步的窗口——避免锁定到偏低的"睡前值"（详见技术架构 6.4）。
- R3.5 （2026-10-26 调整）活动到期后开放**补同步窗口**：仍可同步活动期内步数（写入仅限 [start_date, end_date]，历史日插入即锁）；管理员**终止**活动后才关闭同步入口、排名冻结、所有数据转为只读查看（含历史战绩），并触发积分结算。
- R3.6 防作弊（轻量）：对单日步数异常值（如 > 50000 步）在后台标记 `abnormal=true`，仅作提示不自动剔除；管理员可手动裁定（P0 提供"标记+查看"，不做复杂判定）。

**涉及接口**
| 接口 | 入参 | 出参 |
|------|------|------|
| `POST /steps/sync` | encryptedData、iv | 同步结果、当日步数、累计步数 |
| `GET /steps/today` | — | 今日步数、同步状态 |
| `GET /steps/history` | start_date、end_date | 每日步数列表 |

### F4 步数展示

**用户故事**
> 作为员工，我希望直观看到自己当日和累计的步数及趋势，以便了解自己的运动情况。

**前置条件**
- 用户已报名，且至少完成一次步数同步。

**页面与交互（个人主页）**
| 区域 | 元素 | 说明 |
|------|------|------|
| 顶部数据卡 | 当日步数（大字）、累计步数、活动进度 | 实时反映最新同步值 |
| 趋势图 | 近 7/30 天步数柱状图 | 直观展示趋势 |
| 我的排名 | 全员排名名次（如 35/520） | 点击进入个人排行榜 |
| 操作区 | 「同步步数」按钮、下拉刷新 | 手动触发同步 |

**字段定义**
- 当日步数 `today_steps`、累计步数 `total_steps`、活动期天数 `total_days`、已参与天数 `active_days`、趋势数据 `trend: [{date, steps}]`。

**业务规则**
- R4.1 累计步数 = 活动开始日 ~ 当前已入库的每日步数之和。
- R4.2 趋势图默认展示近 7 天，可切换 30 天。
- R4.3 无同步记录时展示占位文案"暂无数据，请点击同步步数"。
- R4.4 排名为空（未达统计条件）时不展示具体名次，引导完成同步。

**涉及接口**
| 接口 | 入参 | 出参 |
|------|------|------|
| `GET /user/stats` | — | 当日步数、累计步数、参与天数、排名概要 |
| `GET /steps/trend` | range(7/30) | 趋势数据 |

### F5 个人排行榜

**用户故事**
> 作为员工，我希望看到全体员工的步数排名和我的名次，以便激发我的运动积极性。

**前置条件**
- 用户已报名；活动已有至少 2 名参与者产生步数。

**页面与交互**
| 区域 | 元素 | 操作 |
|------|------|------|
| Tab 切换 | 个人榜 / 部门榜 | 切换 |
| 榜单 Top 列表 | 排名、头像、昵称（脱敏）、部门、累计步数 | 滚动加载（分页，如每页 50） |
| 我的排名条 | 固定底部，展示我的名次/步数/前后名次 | 始终可见 |
| 时间范围 | 活动累计（P0 仅累计总榜） | — |

**字段定义**
| 字段 | 说明 |
|------|------|
| rank | 名次 |
| user_id | 用户 |
| nickname（脱敏） | 如"张*明" |
| dept_name | 部门 |
| total_steps | 累计步数 |

**业务规则**
- R5.1 排行榜按活动累计步数降序；同分按 `first_reach_at` 升序排（更早达成者列前）。`first_reach_at` 定义：按 `synced_at` 顺序累加该用户各日 steps，累计值**首次达到（或超过）当前 total_steps** 的那条 StepRecord 的 `synced_at`（详见技术架构 6.3）。
- R5.2 排行榜数据由**定时任务聚合**生成（建议每 10 分钟更新一次），非实时排序，以控制查询压力；榜单顶部标注"数据更新时间"。
- R5.3 昵称脱敏展示（中间字以 * 替代）。
- R5.4 分页加载，默认每页 50 条，支持上拉加载更多。
- R5.5 所有已报名用户（join_status=joined）均进榜，包括 total_steps=0 及从未同步的用户（0 步用户排在榜末）；未报名用户不进榜。

**涉及接口**
| 接口 | 入参 | 出参 |
|------|------|------|
| `GET /rank/personal` | page、page_size | 排名列表、我的排名、总人数、更新时间 |

### F6 部门排行榜

**用户故事**
> 作为员工，我希望看到各部门的团队成绩，以便为所在部门荣誉而走。

**前置条件**
- 至少 2 个部门有已报名成员。

**页面与交互**
| 区域 | 元素 | 操作 |
|------|------|------|
| 部门榜单 | 排名、部门名称、总步数、人均步数、成员数 | 点击部门进入明细 |
| 部门明细页 | 部门内成员排名列表 | 查看本部门同事成绩 |
| 我的部门卡 | 我的部门排名、贡献占比 | — |

**字段定义**
| 字段 | 说明 |
|------|------|
| rank | 部门名次 |
| dept_id / dept_name | 部门 |
| total_steps | 部门累计步数（成员累加） |

**业务规则**

## 8. 非功能需求

### 8.1 性能
- 步数同步接口 P95 < 800ms（含微信解密）。
- 排行榜查询走 RankCache 中间表，P95 < 300ms。
- 排行榜定时聚合频率：每 10 分钟一次（可配置）。
- 个人主页首屏加载 < 1.5s。

### 8.2 安全
- 手机号后端完整存储用于白名单匹配，前端展示与日志均脱敏。
- token 采用短期有效 + 刷新机制；接口统一鉴权。
- `session_key` 仅存后端，不下发前端。
- 后台管理员账号密码加密存储（如 bcrypt）。

### 8.3 步数数据时效口径（重要，影响排名争议）
- 微信运动当日步数通常**次日上午**才稳定准确。
- 累计步数以"已入库"为准；**每日次日 12:00（可配置）**定时锁定前一日最终值并参与排名（给上午同步窗口，避免锁定偏低值）。
- 排行榜标注"数据更新时间"，向用户说明排名基于已同步数据，存在轻微延迟属正常。

### 8.4 防作弊（轻量策略）
- 单日步数 > 50000 标记 `abnormal`（阈值可配置）。
- 后台提供异常列表与手动裁定（忽略 / 置零）。
- P0 不做步数来源深度校验（如设备/轨迹），仅做异常值提示，避免过度投入。
- 同步频率限制：单用户单日同步落库 ≤ 6 次。

### 8.5 兼容性与可用性
- 支持主流 iOS/Android 微信版本（基础库 ≥ 2.10.x，覆盖 `getWeRunData`、`getPhoneNumber`）。
- 用户拒绝授权场景下提供引导重授权路径（`openSetting`）。
- 活动期内服务可用性目标 99%；活动结束数据可长期只读访问。
