## 1. 架构概述

### 1.1 架构选型
- **整体方案**：微信小程序（原生）+ 微信云开发（CloudBase）。
- **后台形态**：小程序内置管理员后台（识别 `is_admin` 身份后路由到 `pages/admin/*`），无独立 Web 站点。
- **适用判断**：单期企业活动、量级可控（千级）、数据可上云、要快上线、无需对接外部系统 → 云开发为最优解。

### 1.2 选型理由
| 关注点 | 云开发如何满足 |
|--------|--------------|
| 免运维 | 无需服务器/域名/Nginx/部署流水线，腾讯云托管 |
| 微信生态集成 | `code2Session`、`getPhoneNumber`、微信运动步数解密为官方最短路径 |
| 上线速度 | 云函数 + 云数据库 + 静态托管开箱即用 |
| 定时任务 | 定时触发器配置即用（排行榜聚合、每日步数锁定） |
| 成本 | 按量计费，千级用户单期活动近乎零成本 |
| 内置后台 | 管理员入口即小程序页面，复用同一云开发环境，一套环境全搞定 |

### 1.3 约束与前提
- 小程序须为**非个人主体**（企业主体），方可使用 `getPhoneNumber` 与云开发。
- 需开通云开发环境（建议按量付费基础版起步）。
- 微信运动 `getWeRunData` 仅微信环境可用，已确认单端微信小程序，无跨端需求。
- 收集手机号 + 微信运动步数属个人信息，须在小程序后台完成**隐私协议配置**并在端内授权弹窗（详见 10.4）。

### 2.1 分层职责
| 层 | 职责 | 说明 |
|----|------|------|
| 前端表现层 | 页面渲染、用户交互、权限路由 | 员工页与管理员页同在小程序内，通过 `is_admin` 控制可见与路由守卫 |
| 云函数业务层 | 业务逻辑、鉴权、微信接口对接、数据校验 | 所有写操作与敏感读操作必须经云函数，禁止前端直写数据库 |
| 云数据库层 | 数据持久化 | 文档型存储；排行榜读 RankCache 中间表 |
| 云存储层 | 二进制资源 | 用户头像、活动头图、规则图文素材、白名单导入文件 |
| 定时触发器 | 异步聚合与锁定 | 排行榜每 10 分钟聚合；每日 12:00 锁定前一日步数 |
| 微信开放能力 | 身份与数据源 | openid、手机号、微信运动步数 |

### 2.2 内置后台实现约定（关键）
后台塞进小程序内能省一个 Web 站点，但有三处必须按以下方式实现，否则会成为 P0 最痛的点：

| 事项 | 约定 |
|------|------|
| **管理员冷启动** | 第一个 `is_admin=true` 账号由**部署人员在云开发控制台手工置位**（按 openid 或手机号定位后改字段），并在运维文档记录该账号。小程序内不提供"自助成为管理员"入口。后续管理员可由已有管理员在后台添加。 |
| **白名单批量导入** | 走「前端选文件（`wx.chooseMessageFile`）→ 上传云存储 → 云函数解析 xlsx/csv」三步。**禁止在前端解析电子表格**（小程序解析能力弱、易错）。云函数用 `xlsx` / `csv-parse` 库解析，去重后批量写入 Whitelist。 |
| **数据看板预期** | 看板在小程序内展示，图表用 ec-canvas；但**大批量表格筛选/分页体验不如 Web**，P0 接受该限制，仅提供必要的筛选（部门、异常标记）与分页。 |

## 3. 技术选型

| 维度 | 选型 | 理由 |
|------|------|------|
| 前端 | 原生微信小程序（WXML/WXSS/JS） | 微信运动仅微信环境可用；单端无需跨端；生态成熟 |
| 前端语言 | JavaScript（ES6+） | 原生小程序标准；团队上手快 |
| 前端请求封装 | `wx.cloud.callFunction` + 自封装 Promise 化工具 | 统一 loading、错误处理 |
| 后端 | 微信云开发云函数（Node.js） | 官方集成最佳；免运维 |
| 数据库 | 云开发云数据库（文档型 NoSQL） | 步数/排名等文档数据友好；聚合查询能力够用 |
| 鉴权 | **以云运行时注入的 `wxContext.OPENID` 为可信身份**；前端登录态由 `wx.login` + `wx.cloud` 自带机制维持 | 云函数可直接拿到微信注入、不可伪造的 OPENID，无需再叠加自管签名 token，省去 token 存储/过期/刷新/多端一致等复杂度 |
| 图表 | `wx-charts` 或 `ec-canvas`（ECharts 小程序版） | 步数趋势柱状图 |
| 列表虚拟滚动 | 小程序原生 `scroll-view` + 分页 | 排行榜分页加载 |
| 日期处理 | `dayjs`（轻量） | 步数按日处理 |
| 电子表格解析（云函数内） | `xlsx` / `csv-parse` | 白名单导入 |

## 4. 云函数设计

### 4.1 云函数划分（按业务域）
| 云函数 | 职责 | 主要 action | 对应 PRD |
|--------|------|------------|---------|
| `auth` | 登录鉴权 | `login` / `phone` | F1 |
| `user` | 用户与报名 | `profile` / `join` / `stats` | F1、F2、F4 |
| `dept` | 部门 | `list` | F2 |
| `activity` | 活动 | `current` / `save` | F7、F8 |
| `steps` | 步数同步与查询 | `sync` / `today` / `history` / `trend` | F3、F4 |
| `rank` | 排行榜（读缓存） | `personal` / `dept` / `deptMembers` | F5、F6 |
| `admin` | 后台管理 | `whitelistImport` / `users` / `changeDept` / `abnormalList` / `verdict` / `dashboard` / `deptManage` | F8 |
| `tasks` | 定时任务 | `rankAggregate`（每 10 分钟）/ `dailyLock`（每日 12:00） | F3、F5、F6 |

> 设计原则：**单云函数多 action**（按 `event.action` 分发），减少云函数数量、复用鉴权中间件；每个 action 独立 handler 文件。`tasks` 的聚合/锁定逻辑同时暴露为可手动触发的 action，便于本地与回归测试（见 6.5）。

### 4.2 云函数调用约定
**统一入参**：
```js
{
  action: 'login',          // 业务动作
  data: { /* 动作参数 */ }
}
// 调用者身份（openid）由云运行时自动注入，云函数内用
// cloud.getWXContext().OPENID 获取。前端无需、也不应传递任何
// 身份凭证或 token —— 鉴权完全依赖微信侧注入的 OPENID。
```

**统一出参**：
```js
{
  code: 0,           // 0=成功；非 0=业务错误码（见附录）
  message: 'ok',
  data: { /* 业务数据 */ }
}
```

### 4.3 鉴权中间件
所有云函数入口先执行 `authMiddleware()`：
1. 取 `cloud.getWXContext().OPENID`（微信运行时注入，不可伪造，**可信身份**）。
2. 查 User 表确认该 openid 存在、且报名状态符合当前 action 要求（如 `steps.sync` 要求 `join_status=joined`）。
3. 管理员类 action 额外校验 `user.is_admin === true`。

- `auth.login` / `auth.phone` 为登录前置，不要求 User 已存在。
- **不使用自管签名 token**：身份完全信任微信侧 OPENID。前端"登录态"由 `wx.login` + `wx.cloud` 自带机制维持（`callFunction` 时框架自动携带凭证），既不下发也不校验任何自管 token。

## 5. 云数据库表结构

> 文档型存储，字段以 JSON 表示。带 🔒 为后端独有/不返回前端。

### 5.1 User（用户）
```jsonc
{
  _id: "u_001",
  _openid: "oABC...",            // 🔒 微信 openid（唯一）；同时也是鉴权身份键
  unionid: "uid...",             // 🔒 可选
  nickname: "张明",
  avatar: "cloud://xxx/avatar.jpg",
  phone: "13812341234",          // 🔒 完整手机号，仅后端
  phone_masked: "138****1234",   // 前端展示
  dept_id: "d_01",
  join_status: "joined",         // pending | joined
  joined_at: "2026-06-26T10:00:00Z",
  is_admin: false,
  // 预留 P1
  // daily_goal: 8000,
  // badge: [],
  created_at, updated_at
}
```
> 不再存储 `token` / `token_expire`：鉴权不依赖自管 token（见 4.3）。

**索引**：`_openid`（唯一）、`phone`（唯一）、`dept_id`、`is_admin`。

### 5.2 Department（部门）
```jsonc
{
  _id: "d_01",
  name: "研发部",
  activity_id: "a_001",
  created_at
}
```
**索引**：`activity_id`、`(activity_id, name)`。

### 5.3 Whitelist（员工白名单）
```jsonc
{
  _id: "wl_001",
  phone: "13812341234",          // 🔒
  imported_at: "2026-06-25T08:00:00Z"
}
```
**索引**：`phone`（唯一）。

### 5.4 Activity（活动）
```jsonc
{
  _id: "a_001",
  name: "2026 员工健步走",
  cover_url: "cloud://xxx/cover.jpg",
  rules: "<rich text>",
  start_time: "2026-07-01T00:00:00+08:00",
  end_time: "2026-07-21T23:59:59+08:00",
  status: "active",              // pending | active | ended（由时间推算冗余）
  total_steps: 0,                // 🔒 全员累计（聚合写回）
  participant_count: 0,          // 🔒 已报名人数（聚合写回）
  created_at
}
```
**索引**：`status`、`start_time`。

### 5.5 StepRecord（步数记录）
```jsonc
{
  _id: "sr_001",
  user_id: "u_001",
  _openid: "oABC...",            // 冗余便于聚合
  activity_id: "a_001",
  date: "2026-07-01",            // YYYY-MM-DD（北京时间）
  steps: 8521,
  abnormal: false,               // 超阈值标记
  locked: false,                 // 每日锁定标记（见 6.4）
  synced_at: "2026-07-01T20:00:00Z"  // 也用于同分排序 first_reach_at 计算
}
```
**索引**：
- `(user_id, activity_id, date)` 唯一约束 —— 云数据库无原生唯一约束，**由 sync 逻辑用事务（或先查后写）保证 upsert**，避免同用户短时多次同步产生重复记录。
- `activity_id + date`（聚合用）
- `abnormal + activity_id`（后台异常查询）

### 5.6 RankCache（排行榜聚合缓存）
```jsonc
{
  _id: "rc_001",
  type: "personal",              // personal | dept
  activity_id: "a_001",
  rank: 1,
  ref_id: "u_001",               // personal=user_id / dept=dept_id
  total_steps: 125000,
  first_reach_at: "...",         // 同分排序键，见 6.3 定义
  // personal 额外（已脱敏，聚合时写入）
  nickname: "张*明",
  dept_name: "研发部",
  // dept 额外
  member_count: 12,
  avg_steps: 10416,
  updated_at: "2026-07-02T00:10:00Z"
}
```
**索引**：`(type, activity_id, rank)`、`(type, activity_id, ref_id)`。
> `extra: object` 的写法已废弃，统一为平铺字段，便于查询与排序。

## 6. 关键时序流程

### 6.1 登录与手机号验证
```
小程序                auth云函数              微信服务器
  │ wx.login code ──►  │                        │
  │                    │ ── code2Session ──►    │
  │                    │ ◄── openid ──          │
  │                    │ 查/建 User（按 openid）  │
  │ ◄── 登录结果 ──    │                        │
  │ （是否已注册/已报名，│                        │
  │   无需返回 token）  │                        │
  │ 授权手机号         │                        │
  │  phoneCode ──►     │                        │
  │                    │ ── getPhoneNumber ──►  │
  │                    │ ◄── phone ──           │
  │                    │ 校验 Whitelist          │
  │ ◄── 校验结果 ──    │                        │
```
> 后续所有 `wx.cloud.callFunction` 由框架自动携带调用者凭证，云函数取 `OPENID` 即完成鉴权；前端不持有任何自管 token。

### 6.2 步数同步（session_key 主路径 —— 不长期存储）
```
小程序                steps云函数              微信服务器
  │ wx.login（取最新 code，本地持有）
  │ wx.getWeRunData → encryptedData+iv
  │  encryptedData+iv+code
  │ ─────────────►    │                        │
  │                   │ ── code2Session ──►    │
  │                   │ ◄── openid+session_key │
  │                   │   （当次新鲜 key）       │
  │                   │ 立即用当次 session_key 解密 stepInfoList（近30天）
  │                   │   ※ 不把 session_key 写入任何表
  │                   │ 对活动期内每日 upsert（事务保证唯一）：
  │                   │   steps>阈值 → abnormal=true
  │                   │ 更新单日同步计数（≤6次）
  │ ◄── 当日+累计 ──  │                        │
```
> **为什么不存 session_key**：微信规则下，每次 `wx.login` 都会使上一次 `code2Session` 返回的 session_key 失效。一旦长存，用户任何一次静默续登都会让存的 key 作废、导致解密失败。改为**每次同步当次换 key、当次解密**，从根上规避失效问题。

### 6.3 排行榜聚合（定时，幂等）
```
[timer 每10分钟] ──► tasks.rankAggregate（也可手动触发，见 6.5）
  ├ 个人榜：按 activity 聚合各 user 的 total_steps
  │         （仅 locked 或今日已入库的有效步数）
  │         排序 → 覆盖写 RankCache(type=personal)
  └ 部门榜：按 dept 聚合 → 算 avg/total → 覆盖写 RankCache(type=dept)
```
**`first_reach_at` 定义（同分排序键）**：某用户"首次达到当前累计步数的时间" = 按 `synced_at` 顺序累加该用户各日 steps，累计值**首次达到（或超过）当前 total_steps** 的那条 StepRecord 的 `synced_at`。同分时该值小者（更早达成）排前。
> P0 实现可简化为：聚合时按用户 `synced_at` 升序遍历累加，命中即记录。

**幂等**：聚合任务以"覆盖写 RankCache"实现，重复执行无副作用，每 10 分钟运行安全。

### 6.4 每日步数锁定（定时，幂等）
```
[timer 每日 12:00（可配置）] ──► tasks.dailyLock
  └ 将 date = (昨日) 的 StepRecord 全部 locked=true
      锁定后即使再次同步也不改变已参与排名的值
```
> **为什么是 12:00 而不是 00:00**：微信运动当日步数通常**次日上午**才趋于准确（PRD R3.4/8.3）。若在 00:00 锁定，锁到的是用户睡前的偏低值；推迟到次日 12:00，给用户整个上午补同步的窗口，锁定值更接近真实。该时间为可配置项，由活动规则最终确定。

**幂等**：重复执行只是把已 `locked=true` 的记录再置 true，无副作用。

### 6.5 定时任务的可测试性
定时触发器无法本地调试，因此 `tasks` 云函数的聚合与锁定逻辑同时暴露为**可手动触发的 action**（`rankAggregate` / `dailyLock`，管理员鉴权）。本地与回归测试时直接调用 action，复用同一份逻辑，避免"线上逻辑测不到"。

### 7.2 云函数内部结构（以 `steps` 为例）

## 8. 安全设计

| 风险 | 措施 |
|------|------|
| 身份伪造 | 身份完全依赖云运行时注入的 `wxContext.OPENID`（微信侧不可伪造）；无需自管 token，反而消除了 token 被窃取/重放的风险面 |
| 越权访问 | 管理员 action 校验 `is_admin`；前端隐藏入口 + 后端强校验双保险 |
| 手机号泄露 | 完整手机号仅后端存用；前端/日志一律脱敏；不下发可信身份信息外的敏感字段 |
| 步数篡改 | 步数唯一来源 `getWeRunData` + 后端解密；前端不可直写 StepRecord |
| 接口滥用 | 单用户单日同步 ≤6 次（云函数计数）；活动终止后关闭同步入口（到期后为补同步窗口，仅活动期内步数可写） |
| session_key 失效 | **不长期存储 session_key**；步数同步时前端每次带最新 `wx.login` code，云函数当次 `code2Session` 取新鲜 key 并立即解密，从根上规避"存的 key 已失效" |
| 步数并发去重 | `(user_id, activity_id, date)` 由 sync 逻辑用事务/先查后写保证唯一，防止同用户短时多次同步产生重复记录 |
| 数据库直写 | 数据库权限规则设为「仅创建者可读写」+ 业务走云函数，禁止前端直接写业务集合 |

## 9. 运维与监控

| 事项 | 方案 |
|------|------|
| 日志 | 云函数自带日志（console），关键链路打点（sync 成功/失败、聚合耗时、锁定条数） |
| 监控 | 云开发控制台查看云函数调用次数、错误率、耗时；异常阈值告警 |
| 备份 | 云数据库可定期导出（JSON）；活动结束归档导出存档 |
| 性能 | 排行榜读 RankCache（P95<300ms）；聚合走定时任务避免实时计算 |
| 容灾 | 云函数无状态可重试；步数同步失败前端提示重试；RankCache 故障可手动触发 `rankAggregate` 重建 |
| 测试策略 | 定时逻辑暴露为手动 action（6.5）便于回归；步数解密用真实 encryptedData 样本验证；并发同步去重用同用户连续两次 sync 验证不产生重复记录 |

## 10. 环境与部署

### 10.1 环境
- 建议两套云开发环境：`dev`（开发联调）与 `prod`（线上）。
- 小程序 `app.js` 中按构建环境切换 `envId`。

### 10.2 发布流程
1. 开发：本地调试云函数 + 小程序开发者工具预览。
2. 联调：上传部署到 `dev` 环境，体验版测试。
3. 上线：云函数部署到 `prod`；小程序提交审核发布。
4. 活动前：管理员后台配置活动 + 导入白名单 + 创建部门 → 发布活动。

### 10.3 数据库权限
- 业务集合（User/StepRecord 等）：仅创建者读写 + 云函数（管理员）操作，前端不直连写。
- Whitelist、RankCache：仅云函数可读写。

### 10.4 上线前置 checklist（外部依赖，常卡审核与上线时间）
> 这些多数不在代码层面，但任一缺失都会阻塞上线。建议在开发启动前与运营/企业侧并行推进。

| # | 事项 | 责任方 | 说明 |
|---|------|--------|------|
| 1 | 企业主体小程序账号 | 企业/运营 | 非个人主体，已完成认证 |
| 2 | 服务类目 | 企业/运营 | 选择合适类目（运动/企业服务方向），通过审核 |
| 3 | `getPhoneNumber` 权限 | 企业/运营 | 非个人主体 + 类目符合要求后可用 |
| 4 | `getWeRunData` 权限 | 企业/运营 | 微信运动数据访问授权 |
| 5 | 隐私协议配置 | 开发+运营 | 后台填写收集「手机号」「微信运动步数」的用途，端内首次授权弹窗 |
| 6 | 云开发环境开通 | 开发 | dev + prod 两套，按量付费基础版 |
| 7 | 管理员冷启动账号 | 开发（部署人员） | 控制台手工置位第一个 `is_admin`，并记录 |
| 8 | 域名/服务器 | — | 云开发方案下**无需**，仅列出以示排除 |

## 11. P0 技术范围与边界

**本期实现**：
- 8 个业务域云函数 + 2 个定时任务（逻辑可手动触发）。
- 6 张数据表 + RankCache 聚合。
- 小程序员工端 + 内置管理员后台。
- 步数同步、排行榜、防作弊标记、每日锁定。

**本期不做（预留）**：
- 勋章/打卡/证书/海报（数据表预留字段，逻辑 P1）。
- 多期活动切换（架构已留 `activity_id`，P0 单实例）。
- 跨端（App/H5）。
- 复杂监控（ELK 等）。
